DESIGN NOTES / COFFEE TETHER

好みを記録するアプリを、
作ったあとに疑う。

コーヒーの味覚ログ「COFFEE TETHER」を、課題設定・設計判断・限界の順に振り返ったノートです。各章のグレーの枠は、実際に触って確かめられます。

HTML / CSS / JS 単体 4軸の味評価 + フレーバータグ ♥ → QR / おすすめ
01

課題設定

解きたいのは「おいしいカフェを探す」ことではなく、「自分にとっておいしい」を、他人の口コミから見つけること。

課題 A　口コミは「書いた人の好み」で書かれている

同じ「酸味が心地いい」でも、酸味を5と感じる人と3と感じる人では、行った後の評価が変わります。口コミを読む前に、自分の位置を知る必要があります。

TRY　自分の酸味の好みを動かす

2

口コミごとの「ズレ」が小さいほど、その人の感想は参考にしやすい、と考えます。

課題 B　好みが言語化できず、記録も散らばる

「酸っぱいのは好き。でも浅煎りは違う」のように、好みは複数の軸にまたがります。メモアプリに書いた感想は、あとで比べられません。

課題 C　空のアプリは使われない

記録がゼロの状態では、おすすめも味覚チャートも出せません。最初の1杯までをどう短くするかが、入口の課題です。

02

設計判断

各判断を「採用案・却下案・理由・代償」の4つで残します。代償は、次の章の「限界」へつながります。

D1味を4軸のスライダーとタグで入力する

採用焙煎度・酸味・苦味・コクを5段階で、香りはタグで選ぶ
却下自由記述のみ
理由数秒で入力でき、レーダーチャートで形として比べられる(課題B)
代償5段階の「4」は人によって違う

代償 → L4 味の評価が主観

D2QRとチャートには「♥した記録だけ」を反映する

採用♥の記録の平均を「マイ・ブレンドパス」にする
却下全記録の平均
理由「行った」と「好き」を分けないと、好みが平均に薄まる(課題A・B)
代償♥が少ないうちは、1件の影響が大きい

TRY　♥を付け外しして、平均を比べる

しま模様が「全記録の平均」です。浅煎りが好きな人の記録に、深煎りが混ざると平均が中央に寄ります。

D3おすすめは「タグの一致数」で決める

採用♥した記録のタグと、口コミのタグの一致数で並べる
却下4軸の数値の距離で並べる類似度
理由「ベリーと紅茶が一致」と理由を言える。数値の近さは説明しにくい
代償口コミが少ないと一致が出ない

TRY　好きなタグを選ぶ

    代償 → L3 おすすめが単純

    D4味覚診断は4問、いつでもスキップできる

    採用二択中心の4問。回答は初期プロフィールと初期タグになる
    却下長い診断、またはスキップ不可
    理由記録ゼロでも最初の画面を空にしない(課題C)。でも、診断で足止めはしない
    代償4問の精度は低く、質問と選択肢のタグが合わないことがある

    代償 → L7 診断のタグ不整合

    03

    限界

    できていないことを、影響の大きさと直す手間で並べました。丸を押すと詳細が出ます。

    影響 大影響 小 手間 大 →まず着手

      限界を実感する　記録はリロードで消える

      現在のアプリは、記録をメモリ上の配列にしか持ちません。「次の一手」を入れると何が変わるか、試せます。

      TRY　記録を足して、リロードを再現する

        次にやること

        1. 記録を localStorage に保存するL1。数十行で済み、影響が最も大きい。
        2. 口コミの件数に応じて、推薦の出し方を切り替えるL3。少ないうちは「最近の口コミ」を出し、増えたら一致数で並べる。
        3. 店舗側がQRを読み取る最小の画面を作るL5。読んだ人が味の傾向を見られる、1画面だけでよい。
        COFFEE TETHER 設計ノート ・ 数値とデータはアプリ本体のサンプルデータに基づきます。
